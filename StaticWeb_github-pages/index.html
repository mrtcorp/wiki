    Publicar web estatica en GitHub Pages con dominio propio¶

    Resumen del proceso para alojar una web, en GitHub Pages mediante git terminal, accesible desde tu.dominio.com con HTTPS.

    1. Qué es GitHub Pages y qué límites tiene¶

    GitHub Pages sirve contenido estático (HTML, CSS, JS ya generados) desde un repositorio. No ejecuta código (php...) en servidor ni ofrece base de datos.

    • Un sitio de usuario por cuenta (usuario.github.io) y un sitio de proyecto por repositorio, así que se pueden alojar tantos sitios como repos. Creando un archivo CNAME que contenga el subdominio (un CNAME para cada web de cada repo), puedes crear diversos registros CNAME en tu servidor de dominio (ovh en mi caso). Seria como tener un proxy inverso
    • El repositorio y el sitio publicado no deben superar 1 GB, y el despliegue falla si tarda más de 10 minutos.
    • No se permiten tiendas online ni servicios comerciales (SaaS), ni para manejar contraseñas o datos de tarjetas.
    • Con cuenta gratuita, el repo debe ser público para poder usar Pages.

    2. Crear el repositorio y activar Pages¶

    1. Crear un repositorio público (aquí, wiki). Con un nombre distinto de usuario.github.io será un sitio de proyecto, con URL https://usuario.github.io/wiki/.
    2. En el repo: Settings → Pages (solo disponible en la web, no en la app de Android). Directo: github.com/<usuario>/wiki/settings/pages.
    3. Configurar:
      • Source: Deploy from a branch.
      • Branch: main, carpeta / (root). Guardar con Save.

    Opciones de la pantalla:

    • Deploy from a branch: publica tal cual lo que haya en una rama y carpeta. Es la más simple.
    • GitHub Actions: compila el sitio en cada push mediante un workflow. Es gratis en repositorios públicos con los runners estándar.
    • Visibility: publicar de forma privada es una función de GitHub Enterprise. No hace falta.
    • / (root) o /docs: carpeta del repo desde la que se publica. Con / (root), el index.html debe estar suelto en el primer nivel.

    Importante: se sube la carpeta site/ (HTML ya generado), nunca docs/ (el Markdown de origen).

    2.1. Problema: cuenta en proceso de eliminación¶

    Si al crear el repo sale "Owner is being deleted, so new repository cannot be created", la cuenta tiene una eliminación pendiente. Hay que cancelarla durante el plazo de gracia (desde la web, en github.com/settings/admin o con el enlace del email de GitHub), o crear una cuenta nueva.

    3. Subir el sitio desde la Raspberry¶

    Comprobar que git está instalado (en este caso, 2.39.5):

    git --version
sudo apt install git   # solo si no está

    Clonar el repo en la carpeta personal, sin sudo y fuera de la carpeta del sitio:

    cd ~
git clone https://github.com/mrtcorp/wiki.git

    Copiar el contenido de site/ dentro del repo y crear .nojekyll:

    cp -r /srv/docker/web/html/site/. ~/wiki/
touch ~/wiki/.nojekyll

    Configurar identidad y subir (desde dentro de ~/wiki):

    git config --global user.name "mrtcorp"
git config --global user.email "<email o email noreply de GitHub>"
cd ~/wiki
git add .
git commit -m "Primera versión de la wiki"
git push

    GitHub no acepta la contraseña de la cuenta para git. Hay que usar un Personal Access Token:

    1. GitHub → foto → Settings → Developer settings → Personal access tokens → Tokens (classic).
    2. Generar uno con el permiso repo y una caducidad razonable.
    3. Copiarlo al momento (empieza por ghp_ y no se vuelve a mostrar).
    4. En el push, usuario = nombre de la cuenta, contraseña = el token. La terminal no muestra nada al pegar; es normal. En Windows Terminal se pega con Ctrl+Shift+V.

    Si el repo es público, cualquiera puede leer la wiki: antes de subir hay que revisar que no contenga contraseñas, tokens ni datos privados.

    4. Dominio propio (wiki.mrtdo.com)¶

    Hay tres piezas: el archivo CNAME del repo, el DNS y los ajustes de Pages.

    1. Archivo CNAME en el repo. Indica a GitHub qué dominio debe servir. Solo contiene el dominio, sin https:// ni barra final:

    cd ~/wiki
echo "wiki.mrtdo.com" > CNAME
git add .
git commit -m "Dominio personalizado"
git push

    2. DNS en OVH (Zona DNS de mrtdo.com):

    • Borrar cualquier registro A, AAAA o CNAME anterior de wiki (no pueden convivir).
    • Crear un registro CNAME: subdominio wiki, destino mrtcorp.github.io. (con el punto final).

    3. Ajustes de Pages: en Custom domain debe aparecer wiki.mrtdo.com (el CNAME lo rellena solo) con el aviso DNS check successful. Después, marcar Enforce HTTPS.

    Comprobaciones de DNS en CMD de Windows:

    nslookup -type=CNAME wiki.mrtdo.com
nslookup -type=TXT _github-pages-challenge-mrtcorp.mrtdo.com

    En la Raspberry, dig requiere sudo apt install dnsutils. También sirve dnschecker.org.

    HTTPS: justo después de configurar el dominio, la casilla Enforce HTTPS aparece deshabilitada porque el certificado aún no se ha emitido. Mientras tanto la web carga por HTTP y el navegador (Brave) muestra una X roja. Es cuestión de esperar, entre minutos y un par de horas. Si pasan más de 24 h: Remove del dominio, esperar un minuto y volver a guardarlo, comprobando después que el CNAME sigue en el repo.

    El archivo CNAME lo crea GitHub si el dominio se escribe desde Settings, pero conviene tenerlo en la copia local para que no se pierda en futuras subidas. Si se quiere que salga siempre del build, se puede crear docs/CNAME en el proyecto de MkDocs (MkDocs copia a site/ los archivos que no son Markdown; el .nojekyll, al empezar por punto, no).

    Verificación del dominio (opcional)¶

    En Settings (de la cuenta) → Pages → Add a domain, con mrtdo.com. Evita que otra cuenta de GitHub reclame un subdominio si algún día se deja de usar. Se verifica con un registro TXT en OVH (subdominio _github-pages-challenge-<usuario>, valor el código que da GitHub). Si no se verifica, basta con borrar el CNAME de OVH cuando se deje de usar Pages.

    5. Flujo de actualización¶

    Antes, el flujo era:

    docker exec mkdocs mkdocs build && sudo rsync -a --delete /srv/docker/mkdocs/site/ /srv/docker/web/html/site/

    Ahora se añade un segundo rsync hacia el repo y el push. Se define como función en ~/.bashrc (no como alias, por las comillas y el $(date)):

    site() {
  docker exec mkdocs mkdocs build && \
  sudo rsync -a --delete /srv/docker/mkdocs/site/ /srv/docker/web/html/site/ && \
  rsync -a --delete --exclude='.git' --exclude='CNAME' --exclude='.nojekyll' /srv/docker/mkdocs/site/ /home/mpi/wiki/ && \
  git -C /home/mpi/wiki add . && \
  { git -C /home/mpi/wiki commit -m "Actualización $(date '+%F %H:%M')" || true; } && \
  git -C /home/mpi/wiki push
}

    Conceptos clave:

    • rsync --delete borra del destino lo que ya no existe en el origen. El origen nunca se toca. La carpeta destino permanece; solo cambia su contenido.
    • --exclude protege del borrado .git, CNAME y .nojekyll.
    • Orden y barra final: origen primero, destino después; site/ con barra copia el contenido, sin barra crearía una carpeta anidada. Para probar sin cambiar nada, añadir --dry-run (las líneas deleting son lo que se borraría).
    • cp -r origen/. destino/ solo añade y sobrescribe; no borra, así que no elimina el CNAME. mkdocs build solo limpia site/, no ~/wiki.
    • git add . prepara los cambios (nuevos, modificados y borrados, en git moderno) para el commit; git add -A hace lo mismo desde cualquier carpeta. git -C <ruta> ejecuta git en esa carpeta sin cambiar de directorio.
    • || true evita que la cadena se corte cuando no hay nada que confirmar.
    • && encadena pasos: si uno falla, los siguientes no se ejecutan, de modo que no se sube una versión a medias.
    • .git es una carpeta oculta con el historial, las ramas y la configuración del repo (incluido el remoto). Si se borra, ~/wiki deja de ser un repositorio.
    • .nojekyll evita que GitHub procese el sitio con Jekyll, que ignora archivos y carpetas que empiezan por guion bajo.

    Si existía un alias site=..., hay que comentarlo y ejecutar unalias site antes de source ~/.bashrc; si no, bash sustituye el alias dentro de site() { y da un error de sintaxis.

    6. Que el push no pida usuario ni token¶

    Opción recomendada: clave SSH como deploy key (da acceso solo a ese repo):

    ssh-keygen -t ed25519 -C "raspberry-wiki" -f ~/.ssh/id_wiki
cat ~/.ssh/id_wiki.pub
    1. En el repo: Settings → Deploy keys → Add deploy key, pegar la clave pública y marcar Allow write access.

    2. En ~/.ssh/config:

      Host github-wiki
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_wiki
  IdentitiesOnly yes

    3. Cambiar el remoto y probar:

      git -C ~/wiki remote set-url origin git@github-wiki:mrtcorp/wiki.git
git -C ~/wiki push

    Alternativa rápida: git config --global credential.helper store. Guarda el token en texto plano en ~/.git-credentials, con acceso a toda la cuenta, y caduca.

    7. Problemas encontrados y soluciones¶

    Síntoma Causa Solución
    Owner is being deleted... al crear el repo Cuenta con eliminación pendiente Cancelar la eliminación o usar otra cuenta
    Permission denied al clonar dentro de site/ Carpeta propiedad de root Clonar en ~ sin sudo
    fatal: not a git repository Comando ejecutado fuera de ~/wiki cd ~/wiki o usar git -C ~/wiki
    Password authentication is not supported GitHub no admite contraseña de cuenta Usar un Personal Access Token
    syntax error near unexpected token '(' en site() { Alias site antiguo aún cargado unalias site y source ~/.bashrc
    Enforce HTTPS deshabilitado Certificado aún no emitido Esperar; reintentar el dominio si pasan 24 h
    X roja en el navegador Carga por HTTP antes de activar HTTPS Esperar al certificado
    Los cambios no se ven Retardo de publicación y caché (1-2 min o más) Mirar la pestaña Actions del repo y recargar con Ctrl+F5
    Lista de Markdown sin formato Falta línea en blanco antes de la lista Dejar una línea vacía entre el párrafo y la lista

    8. Avisos¶

    • El aviso de Material for MkDocs sobre MkDocs 2.0 (plugins y temas dejarán de funcionar) es informativo. Conviene fijar la versión de la imagen de Docker para no actualizar a ciegas.
    • Una página que no está en nav se publica igualmente, pero no aparece en el menú.
    • El repo es público: no subir secretos. Guardar el token y la clave privada (~/.ssh/id_wiki) con cuidado, y si se exponen, revocarlos en GitHub.
